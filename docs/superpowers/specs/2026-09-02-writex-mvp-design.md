# WriteX MVP 设计规范

- 状态：已批准
- 日期：2026-09-02
- 阶段：MVP
- 产品形态：本地 CLI

## 1. 产品定义

WriteX 是一个面向中文长篇文学创作的工作流系统。它不以“一次生成大量文字”为目标，而是把故事开发、人物建档、长期规划、场景写作、独立评审、定向修订和连续性维护组织为可执行、可检查、可恢复的创作过程。

第一阶段只验证一件事：完整工作流能否稳定提高原创中文长篇小说的可读性，并连续生成五章而不发生明显的人物、时间线或世界观崩坏。

WriteX 的首个风格方向是原创的“青春幻想、宿命感、克制抒情”。“赛博江南”只能作为早期内部讨论代号；产品、代码、配置和对外传播均不得声称复刻特定在世作家，也不得依赖其专有角色、世界观、标志性情节组合或可识别表达。

## 2. 商业验证路径

MVP 不直接建设 SaaS 收费、内容分发或自动投稿能力。近期商业验证路径是：

1. 使用 WriteX 辅助创作完整长篇小说，投稿或连载到网文平台。
2. 使用 WriteX 辅助创作更偏文学性的作品，投稿到文学平台。
3. 以作品是否达到投稿水准、是否能持续吸引真实读者作为产品价值验证。

因此，MVP 优先级依次是文学质量、长程一致性、过程可控、成本可观测。生成速度和界面精致度不构成第一阶段核心竞争力。

## 3. 创作公理

WriteX 的核心公式是：

> 受欢迎的小说 = 永恒情感 × 新鲜处境 × 艰难选择 × 人物真实性 × 叙事控制

五个维度的含义如下：

| 维度 | 系统含义 |
| --- | --- |
| 永恒情感 | 人物的普遍欲望、恐惧、关系需求和作品情感承诺 |
| 新鲜处境 | 承载古老情感的新颖、具体且可信的外部处境 |
| 艰难选择 | 无法两全且包含真实代价的行动选择 |
| 人物真实性 | 行为由人物经历、认知、欲望和当前状态自然产生 |
| 叙事控制 | 对信息、视角、节奏、画面、潜台词、意象和情绪释放时机的控制 |

乘法关系不是一句宣传语。系统必须防止任何高分维度掩盖致命短板，并在计划、写作和审稿阶段持续保存五个维度的证据。

## 4. 目标与非目标

### 4.1 MVP 目标

- 提供从故事立项到连续五章正式稿的完整 CLI 工作流；五章是用于验证工作流的 MVP 边界，不是长篇创作的最终形态。后续扩展到完整长篇时，核心双循环模型和章节生产流程无需推倒重来，但需要升级长程规划、分卷与阶段性状态管理、跨卷连续性审计、伏笔与人物弧追踪、上下文检索和版本分支能力，并将固定的“五章一次审计”扩展为按卷、按阶段和风险触发的多层审计机制。正式稿生产也应从连续生成转为可暂停、可回溯、可局部重写的增量工作流，避免前期变更导致全书状态失控。 rel="nofollow"
- 使用结构化文件维护人物、关系、时间线、伏笔、意象和章节状态。
- 对同一场景生成侧重点不同的三个匿名候选稿。
- 使用独立评审和定向修订提高候选稿质量。
- 通过硬门槛、可配置权重、加权几何总分和独立否决项控制质量。
- 记录每次运行的输入、输出、模型参数、评分证据、成本和耗时。
- 支持中断恢复，且不因失败污染正式稿或正典状态。
- 通过人工盲选验证完整工作流相对于一次性提示词基线的提升。

### 4.2 MVP 非目标

- 不开发桌面或 Web 界面。
- 不开发多人协作、账号、支付或云端托管。
- 不自动发布或投稿到外部平台。
- 不同时支持大量文学类型。
- 不进行模型微调。
- 不使用未获授权的小说全文建立检索库。
- 不保证机器评分等同于平台读者或编辑的最终审美。
- 不把 DeepSeek Harness、Codex 或任一模型供应商变成作品格式的强依赖。

## 5. 已评估的实现路径

### 5.1 直接 fork DeepSeek Harness

优点是能快速获得完整 Agent 运行环境。缺点是上游仍处于 Developer Preview，兼容性变化会直接侵入文学工作流和作品数据，长期维护风险过高。

### 5.2 Python 原型

优点是模型实验和数据分析便捷。缺点是会与 DeepSeek Harness/Cordis 的 TypeScript 插件生态形成双语言边界，并增加后续 CLI、类型契约和插件维护成本。

### 5.3 独立 TypeScript Core 加运行时适配器

这是选定方案。WriteX 自己拥有文学领域模型、工作流状态机、作品文件格式和质量体系；模型供应商与 DeepSeek Harness 均通过适配器接入。

## 6. 技术架构

### 6.1 基础技术决策

- Node.js 与 TypeScript。
- ESM 模块。
- pnpm workspace 单仓库。
- CLI-first。
- Markdown 保存人类主要阅读和编辑的内容。
- YAML 保存配置与较短的结构化正典。
- JSON/JSONL 保存事件、运行记录及机器密集读取的数据。
- WriteX Core 不依赖具体模型供应商或 Harness。
- DeepSeek Harness/Cordis 通过独立适配器接入。

### 6.3 包职责

| 包 | 唯一职责 |
| --- | --- |
| `contracts` | 定义工作流命令、领域对象、运行记录和插件接口的版本化类型 |
| `core` | 执行状态机、步骤调度、运行恢复、取消和事务边界 |
| `workspace` | 读写、校验和迁移作品工作区，不包含文学决策 |
| `model-gateway` | 把统一生成请求映射到具体模型提供方，记录用量和原始响应 |
| `workflow` | 实现立项、规划、场景生产、章节验收和长程审计 |
| `quality` | 实现评分、硬门槛、否决项、评审分歧和修订决策 |
| `prompt-runtime` | 组装有预算的上下文并渲染版本化提示模板 |
| `adapter-dsh` | 将 WriteX 接口映射到 DeepSeek Harness/Cordis 服务与事件 |

各包通过 `contracts` 中的接口交互。除 `adapter-dsh` 外的包不得导入 DeepSeek Harness/Cordis 类型。

### 6.4 关键接口

```ts
interface ModelGateway {
  generate(request: GenerationRequest): Promise<GenerationResult>
}

interface WorkspaceStore {
  readSnapshot(ref: SnapshotRef): Promise<NovelSnapshot>
  stageChanges(runId: string, changes: StateChange[]): Promise<StagedChangeSet>
  commit(staged: StagedChangeSet): Promise<CommitResult>
  rollback(staged: StagedChangeSet): Promise<void>
}

interface WorkflowStep<I, O> {
  name: string
  version: string
  execute(input: I, context: RunContext): Promise<O>
}

interface QualityEvaluator {
  evaluate(candidate: AnonymousCandidate, rubric: QualityRubric): Promise<Evaluation>
}
```

MVP 提供两种运行方式：

1. `direct`：CLI 直接使用一个 OpenAI-compatible Chat Completions 适配器，配置项固定为 `base_url`、`api_key_env`、`model` 和生成参数。它用于尽早运行文学实验。
2. `dsh`：`adapter-dsh` 将相同的 `ModelGateway` 和工作流事件映射到锁定版本的 DeepSeek Harness/Cordis。上游升级只允许影响该包及其契约测试。

测试使用确定性的 Fake Model。供应商专有能力不得出现在文学领域契约中；如果未来接入与 Chat Completions 不兼容的协议，应新增提供方适配器，不修改工作流对象。

## 7. 作品工作区

每部小说是一个独立目录，作品文件可直接阅读、编辑和使用 Git 管理。

```text
novel/
├── writex.yaml
├── brief.md
├── canon/
│   ├── world.md
│   ├── characters/
│   └── relationships.yaml
├── outline/
│   ├── main-arc.md
│   ├── volumes/
│   └── chapter-cards/
├── state/
│   ├── timeline.json
│   ├── character-knowledge.json
│   ├── motif-ledger.json
│   └── promises.json
├── manuscript/
├── drafts/
├── reviews/
└── .writex/
    ├── runs/
    ├── events.jsonl
    ├── snapshots/
    └── staged/
```

### 7.1 文件语义

- `brief.md` 定义题材、目标读者、情感承诺、原创边界和预期篇幅。
- `canon/` 是当前有效的世界与人物事实。
- `outline/` 是可修订的因果规划，不等同于已经发生的事实。
- `state/` 是随正式稿推进的机器可校验状态。
- `drafts/` 和 `reviews/` 可以被替换或删除，不改变正典。
- `manuscript/` 只保存已通过章节验收并由用户接受的正式稿。
- `.writex/` 保存运行基础设施数据，不承载唯一的人类创作内容。

### 7.2 状态原则

- 文件是事实来源，不依赖隐藏数据库才能恢复作品。
- 草稿生成不得直接修改正典或正式稿。
- 章节接受后，状态变更与正式稿在同一事务中提交。
- 事件只追加，不覆写；可从事件定位任一产物的来源。
- 分叉必须同时分叉正文引用、正典快照和状态引用。

## 8. 文学工作流

### 8.1 双循环模型

```text
长程循环：立项 → 故事开发 → 正典 → 全书规划 → 分卷规划 → 长程审计
                                         ↓                    ↑
场景循环：章节合同 → 场景节拍 → 三稿竞争 → 评审 → 修订 → 章节验收
```

长程循环维护作品承诺与因果方向；场景循环生产正文。场景循环只能提出正典变更候选，不能自行重写长程承诺。

### 8.2 阶段定义

#### 创作立项

输出目标读者、题材、作品情感承诺、核心母题、原创边界和预期篇幅。

#### 故事开发

至少提出三个“永恒情感＋新鲜处境”候选，比较其人物潜力、长篇可持续性、差异化和代价结构。用户确认一个故事内核后才能建档。

#### 正典建档

人物记录必须包含公开面具、真实欲望、恐惧、自我谎言、秘密、依恋对象、已知事实、误解、崩溃点、说话习惯和可发生变化的条件。

#### 全书与分卷规划

规划主线因果、人物弧、关系弧、秘密揭露顺序、伏笔、意象及结局代价。规划不得退化为相邻章节摘要列表。

#### 章节规划

每章必须生成并校验以下合同：

```yaml
purpose: 本章为什么存在
viewpoint: 视角人物
desire: 人物当前想得到什么
situation: 新出现的具体处境
choice: 必须作出的选择
cost: 选择造成的损失
relationship_shift: 关系如何改变
state_changes: 哪些正式状态会变化
ending_pressure: 推动继续阅读的未完成压力
```

缺少 `purpose`、`choice`、`cost` 或至少一项有效状态变化的章节不得进入正文生成。

#### 场景生产循环

1. 场景导演将章节合同拆为可观察的场景节拍。
2. Context Compiler 按权限与预算组装当前场景上下文。
3. 三名写作者生成匿名候选稿：
   - A：人物与潜台词优先；
   - B：场面调度与叙事清晰度优先；
   - C：情绪积累与释放优先。
4. 独立评审器输出分数、证据、诊断和修改指令。
5. 编排器选择最佳基础稿并执行定向修订。
6. 修订稿作为新候选重新评审，不继承旧分数。
7. 达到门槛后进入章节合并；否则继续修订或停止等待人工处理。

#### 章节验收

合并场景后重新检查章节整体节奏、重复信息、情绪曲线、章节合同和状态变化。只有用户接受的通过稿才提交到 `manuscript/`。

#### 长程审计

默认每五章执行一次，并允许风格包或作品覆盖频率。审计人物弧停滞、情感承诺偏离、伏笔遗忘、配角工具化、节奏单调以及压抑/释放失衡。

### 8.3 人工确认点

MVP 默认只有三个强制人工确认点：

1. 故事内核与主要人物。
2. 全书方向和每卷方向。
3. 每章最终正式稿。

场景生成、评审和限定轮次内的修订自动执行。用户可以随时查看、替换或重跑任一步骤。

## 9. 质量系统

### 9.1 评分机制

每个维度评分范围为 0 至 100，权重总和必须为 1。候选稿只有在每个维度都达到硬门槛、无否决项且总分达到要求时才通过。

总分为归一化的加权几何平均：

```text
Q = 100 × ∏(score_i / 100) ^ weight_i
```

任一 `score_i` 为 0 时，总分为 0。实现必须使用对数形式计算以避免浮点下溢，并拒绝负分、超过 100 的分数、负权重或权重总和不为 1 的配置。

### 9.2 配置继承

```text
系统默认值 → 风格包 → 当前作品 → 单次实验覆盖
```

后一级只覆盖明确提供的字段。合并后的最终配置必须完整校验并写入运行记录，保证结果可复现。

示例：

```yaml
quality_gate:
  scale: 100
  dimensions:
    eternal_emotion: { weight: 0.25, minimum: 65 }
    fresh_situation: { weight: 0.15, minimum: 60 }
    difficult_choice: { weight: 0.20, minimum: 65 }
    character_truth: { weight: 0.25, minimum: 70 }
    narrative_control: { weight: 0.15, minimum: 65 }
  passing:
    minimum_total: 72
    require_every_dimension: true
    max_revision_rounds: 3
```

### 9.3 评审结果

每个维度都必须返回：

```yaml
score: 61
evidence:
  - 主角此前刻意回避冲突，本场景却无铺垫地主动挑衅
diagnosis: 行为转折缺少可观察的触发事件
revision_instruction: 在对话前加入触碰其核心伤口的具体行为
```

证据必须指向候选稿中的具体片段或结构事实。缺少证据的评分视为无效，不参与总分。

### 9.4 独立否决项

- 人物知道了其当前不应知道的信息。
- 时间线、世界规则或已提交正典发生硬冲突。
- 没有完成章节合同规定的关键变化。
- 修订破坏已经成立的伏笔、人物关系或因果链。
- 出现特定作品的专有设定、标志性人物关系或高度相似表达。
- 结构化产物不完整，无法安全推导状态变更。

否决项不能通过提高其他维度权重绕过。

### 9.5 评审分歧

当同一维度不同评审分差大于 20 分时，自动增加一次裁决评审。裁决器必须读取双方证据而非评审身份。若裁决后仍无法形成有效结论，运行状态改为 `needs-human-review`。

## 10. 上下文与提示运行时

不同步骤只能读取完成任务所需的上下文：

- 写作者读取场景合同、必要正典、相关人物状态、最近正文和风格规则。
- 评审器读取匿名候选稿、章节/场景合同和评分量表，不读取模型或作者身份。
- 连续性检查器读取正典、时间线、人物知识和候选状态变更。
- 原创性检查器读取原创边界和当前作品内部语料，不检索特定在世作家小说全文。

Context Compiler 必须为每类上下文设定预算和优先级。无法容纳必须项时，步骤失败并报告超限来源，禁止静默截断正典或时间线。

所有提示模板均包含稳定 ID 与版本号，并在运行记录中保存最终渲染输入的摘要和内容哈希。

## 11. CLI 交互

目标命令面如下：

```text
writex novel init <path>
writex story develop
writex canon build
writex outline build
writex chapter plan <number>
writex chapter write <number>
writex chapter review <number>
writex chapter accept <number> --candidate <id>
writex audit --through <number>
writex run show <run-id>
writex resume <run-id>
writex status
```

所有会改变正典或正式稿的命令默认显示变更摘要。仅 `chapter accept` 及等价的明确用户操作可以提交正式章节和伴随的状态变更。

CLI 使用非零退出码表示失败，标准错误输出简短诊断，详细信息写入对应运行目录。`--json` 模式提供稳定的机器可读输出，供 Harness、脚本和未来桌面端调用。

## 12. 失败处理与恢复

- 每次工作流执行生成唯一 `run_id`。
- 每个步骤使用由运行 ID、步骤名、步骤版本和输入哈希组成的幂等键。
- 模型超时和进程中断后，从最近成功步骤恢复。
- 结构化输出失败时，最多执行两次有记录的格式修复；仍失败则停止。
- 原始模型响应始终保留，格式修复不得覆盖原文。
- 正典更新先写入 `.writex/staged/<run-id>/`，全部校验通过后再提交。
- 事务提交失败时回滚已写入的临时变化；事件记录保留失败事实。
- 达到最大修订轮数仍未通过时进入 `needs-human-review`，不自动接受低质量稿。
- 用户取消运行后不继续发起新模型请求，已完成响应仍记入运行记录。

## 13. 测试与文学评测

### 13.1 工程测试

- 配置继承与完整校验。
- 加权几何平均及边界输入。
- 状态机合法/非法迁移。
- 工作区读写、快照、事务、回滚和迁移。
- 幂等恢复与取消。
- CLI 退出码及 `--json` 输出契约。

### 13.2 工作流测试

使用 Fake Model 和固定夹具完成：

- 章节合同校验。
- 三稿生成与匿名化。
- 评审证据校验。
- 评审分歧裁决。
- 定向修订与重新评分。
- 章节接受和原子状态提交。
- 五章长程审计触发。

### 13.3 文学评测

文学评测不使用固定正文作为唯一正确答案。评测集包含多个原创情境，并检查：

- 是否产生有代价的真实选择；
- 人物行为是否有经历、信息和触发条件支撑；
- 情绪是否主要通过动作、环境、潜台词和意象传递；
- 场景结束后是否发生信息、关系、危险或自我认知变化；
- 是否存在 AI 套话、直接总结、空洞抒情或比喻堆砌；
- 是否违反正典和原创边界。

### 13.4 人类盲测

同一故事输入分别通过完整 WriteX 工作流和一次性提示词基线生成。基线必须使用相同模型、相同模型参数、相同故事输入和近似的总输出 token 预算，但只允许一次正文生成，不使用三稿竞争、独立评审、修订或长期状态更新。隐藏来源并随机左右顺序，记录用户更愿意继续阅读的版本及简短原因。不得用机器评分替代这一指标。

## 14. MVP 验收标准

- 使用三组完全不同的原创故事种子。
- 每组连续生成五章，每章目标 3000 至 5000 字。
- 正式稿不存在已知的时间线、人物知识或世界规则硬冲突。
- 至少完成 30 组匿名 A/B 人工比较。
- 完整 WriteX 工作流稿相对一次性生成基线的盲选胜率达到 70%。
- 所有拒绝、低分和修订都有可追踪证据。
- 每章记录模型、token、估算成本、耗时、失败次数和修订次数。
- 中断恢复测试证明不会重复提交正典或损坏正式稿。
- 所有工程测试、工作流测试和静态检查通过。

达到上述标准代表工作流具备继续创作和投稿实验的价值，不代表作品必然签约或获得商业成功。

## 15. 参考边界

- DeepSeek Harness 仅作为可接入的 Agent 运行时和插件体系参考。其 Developer Preview 状态要求 WriteX 维持独立 Core 和适配器边界。
- Codex 主要提供持久本地工作区、CLI 自动化、Skills/Plugins 和可检查变更的产品范式参考。
- WriteX 的核心知识产权是文学领域契约、双循环工作流、状态模型、质量体系、评测集及积累的人类偏好数据。

## 16. 已确认决策

1. CLI-first，桌面端进入后续阶段。
2. 核心公式采用五维乘法结构。
3. 质量控制采用硬门槛、可调权重、加权几何平均和独立否决项。
4. 作品使用文件工作区，接受章节后才推进正式状态。
5. 工作流采用长程循环与场景循环。
6. 编排器控制有类型步骤，不使用自由对话式 Agent 群。
7. 三个强制人工确认点分别位于故事内核、全书/分卷方向和最终章节。
8. 技术栈采用 Node.js、TypeScript、ESM 和 pnpm workspace。
9. WriteX Core 独立于 DeepSeek Harness、Codex 和具体模型供应商。
10. MVP 以连续五章、无硬冲突和盲测提升作为完成标准。

本设计获仓库内复核后，下一步应编写分阶段实施计划。第一实施切片只建立工程骨架、领域契约、质量计算和可事务化的作品工作区；在这些基础设施通过测试前，不接入真实文学生成工作流。
